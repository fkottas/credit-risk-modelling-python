# Writing and empirical standard

Every chapter follows the same application-first pattern:

1. decision or accounting problem;
2. data unit, target, observation window, performance window, and as-of date;
3. minimum mathematics needed to implement the method;
4. reproducible Python example;
5. controls, failure modes, and leakage checks;
6. interpretation in business units rather than metrics alone;
7. regulatory/accounting boundary;
8. validation and monitoring tests;
9. exercises using at least two compatible datasets;
10. references, dataset attribution, and code entry points.

Tables and figures must be generated by code. Manual numbers are prohibited unless clearly labelled as a hand-worked illustration and checked by a unit test. All random examples use a fixed seed. Metrics must identify the evaluation sample and date split.

The manuscript uses `modelling` in prose and standard Python naming in code. Terms such as default, cure, write-off, Stage 2, downturn, calibration, and approval are never used without the relevant operational definition.
